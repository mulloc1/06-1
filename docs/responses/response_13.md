# 질문 13 — 가설 → 검증과 로그 활용

## 질문

트러블슈팅에서 `가설 → 검증` 순서를 유지한 이유와 로그·근거를 어떻게 활용했는가?

## 답변

증상만 보고 여러 설정을 동시에 바꾸면 어떤 변경이 원인을 해결했는지 알 수 없고 새로운
오류를 만들 수 있다. 먼저 가능한 원인을 한 문장으로 가정하고, 그 원인만 판별하는 관측을
선택하면 최소 변경으로 결론을 낼 수 있다.

이번 실습에서는 “Nginx는 정상이지만 Security Group의 HTTP 규칙이 없으면 외부 요청만
실패한다”를 가설로 세웠다.

1. **기준 상태**: TCP 80 규칙 존재와 외부 `/health` 200을 기록했다.
2. **재현**: TCP 80의 `0.0.0.0/0` 규칙 하나만 제거했다.
3. **검증**: 외부 요청은 타임아웃됐지만 SSH로 실행한 localhost `/health`는 `200/OK`였다.
4. **판단**: 프로세스나 애플리케이션 장애가 아니라 외부 인바운드 경로의 SG 문제였다.
5. **복구**: 동일한 HTTP 규칙을 복원했다.
6. **결과**: 외부 `/health`가 다시 `200/OK`로 회복됐다.

각 명령에는 UTC 시각, 제한된 명령 표시, 출력·오류와 종료 코드를 남겼다. 실패 로그도
삭제하지 않아 가설을 지지하는 근거로 사용했다. Access Key, Session Token과 Private Key는
로그에 남기지 않았다.
